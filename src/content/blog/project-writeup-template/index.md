## What I Was Trying To Prove

Write the real reason you built the project. Avoid broad industry framing at first.

Good prompt: "I wanted to see whether..."

## What I Tried First

Name the first version, shortcut, or assumption. This is where the post starts sounding like it came from the person who built it.

## What Felt Wrong

Explain the gap, rough edge, or failure mode that made you change direction.

## The Design I Settled On

Describe the architecture in your own words. Keep it practical.

Use screenshots beside the post folder and reference them like this:

```md
![What this screenshot proves](./screenshot-name.png)
```

## Key Code Or Config

Use fenced code blocks with language names:

```yaml
apiVersion: example.io/v1
kind: Example
metadata:
  name: real-config-snippet
```

## What The Screenshot Proves

Do not just drop in an image. Tell the reader what they are looking at and why it matters.

## Result

Write the proof point: latency changed, a policy blocked something, deploy time dropped, recovery got simpler, or an operator workflow became safer.

## What I Would Improve Next

End with honest tradeoffs. This is one of the easiest ways to make the post feel real instead of polished into nothing.
